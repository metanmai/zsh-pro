# Adversarial Review — Phase 4 Manifest Builder + Emit

Panel of 5 independent Opus lens reviewers (correctness, risk, requirement-coverage, security, simplicity),
each told to REFUTE and to flag any load-bearing plan claim lacking a PROVEN/STATIC-VALIDATED EVIDENCE entry as HIGH.

## Cycle 1

Per-lens HIGH (from return lines): correctness=4, risk=4, requirement-coverage=3, security=3, simplicity=2 → **HIGH_COUNT=16** (raw sum; heavy cross-lens overlap).

### Consensus HIGH concerns (deduplicated → 8 distinct)

**CH-1 — Ownership-aware PATH restore: refuted mechanism (C11) shipped; scope confusion.** (risk, requirement-coverage, security, simplicity — 4 lenses)
`RebuildListFromBase{Additions}` carries only THIS profile's additions; `Diff(A,nil)` has no representation of other active profiles, and emit renders it as `PATH="$ZP_BASE_PATH"; path=(<additions> $path)`. Under `typeset -U path`, two *managed* profiles co-owning an entry can't be resolved. **Resolution direction (planner):** v2.0 is single-active-profile per terminal (Phase 3 D-13) — two simultaneously-active *managed* profiles is NOT a runtime state. SPEC Req 6 criterion 3's example (`/usr/local/bin`) is **base**-owned; rebuild-from-base inherently preserves base entries, satisfying it for the single-profile model. So: (a) rescope the property-test ownership sub-check to **base-ownership** (base owns `/usr/local/bin`, profile also adds it, deactivate preserves it via rebuild-from-base), NOT two active managed profiles; (b) document multi-managed-profile co-ownership as out-of-scope for single-active v2.0 (defer to a share/Phase-5+ concern where the active set lives); (c) ensure the deactivate list op has DISTINCT semantics from the activate op (rebuild-to-base, not re-add this profile's additions).

**CH-2 — Property-test snapshot instrument is exported-names-only (reintroduces C19 false-green).** (correctness, risk)
The plan reuses `introspectScript`'s `##ENV##` section, which is `[[ $v == *export* ]]`-filtered (exported vars, NAMES only). This is exactly the C19 false-green (a leaked non-exported var, or a clobbered value on an exported var, passes byte-identical). **Fix:** the property test must use a NEW full-env snapshot section iterating ALL `${(@kv)parameters}` (exported AND non-exported), emitting name+VALUE with multi-line-safe (NUL) framing; assert it would fail on a non-exported/value-only residue.

**CH-3 — Runtime undo globals pollute the full-env snapshot; no deactivate cleanup spec.** (correctness)
Emitted apply creates `ZP_BASE_PATH`, `__ZP_ORIG_*`, `ZP_<profile>_PRIOR_*`, sentinels. A full-env (CH-2) snapshot after apply→deactivate sees them as newly SET → spurious fail, or a silent filter hides real residue. **Fix:** decide+state explicitly — either deactivate unsets its own undo slots (add cleanup ops + test), OR the snapshot excludes the `ZP_`/`__ZP_` namespace via an audited, documented filter.

**CH-4 — Shadow prior is never captured at apply time.** (correctness)
`AddAlias`/`AddFunc` emission says nothing about capturing the pre-existing shadowed body BEFORE overwrite; only `SetScalar` captures the live prior. Without capture-before-overwrite (guarded by `${+name}`), `$prior` is never populated and shadow restore cannot pass. **Fix:** specify that `AddAlias`/`AddFunc` emit a `${+name}`-guarded capture-before-overwrite into the shadow-prior slot; add an apply-side capture test.

**CH-5 — Mutated-emitter negative check incompatible with stateless `Provider{}`; too narrow; not independently asserted.** (correctness, requirement-coverage, security)
The negative check needs a flag/variant, but `Emit` is a method on zero-value `Provider struct{}` (no fields to flip). **Fix:** factor the PATH-rebuild (and value-quoting) rendering into an injectable package-level func the test can substitute; add a SECOND mutant that drops zquote on a static metacharacter value (injection-class, not only PATH-append); add an explicit assertion/meta-test that each mutant produces a non-empty diff / fired canary, independent of the happy path.

**CH-6 — `[[ $e == $target ]]` is glob matching, not literal-equality (reintroduces the C10 bug).** (security)
zsh pattern-matches the unquoted RHS of `==` inside `[[ ]]`: `[[ /opt/toolX == /opt/tool* ]]` MATCHES. A PATH element containing `? * [ ]` over-matches — the exact C10 collateral-deletion hazard. **Unvalidated claim** (POC-Z6c only tested `${path:#}`). **Fix:** quote the RHS — `[[ $e == "$target" ]]` — add a POC/EVIDENCE entry proving the quoted form is literal, and a residue-test PATH element containing a metacharacter.

**CH-7 — `RestoreOption{Name, WasOn bool}` built from data the builder is forbidden to author.** (requirement-coverage)
D-06 says `was_on` is a runtime-captured LIVE fact, never authored into the manifest — yet `Diff` builds `RestoreOption{WasOn}` from the manifest where `WasOn` is structurally always the zero value, so "exact was_on restore" (emit) can't be honored from Go-side data. **Fix:** specify that option-reverse reads the runtime-captured `was_on` slot (like scalars/shadows), and mark the op's `WasOn` field non-authoritative (or drop it).

**CH-8 — SchemaV1 "forward-compat gate" is only a `const`, not enforced (T-04-01 unmitigated).** (security, risk)
The threat register dispositions T-04-01 "mitigate" on the basis that SchemaV1 is "a gate checked before reverse logic," but no code reads `Manifest.Schema` and rejects a mismatch — the only acceptance is `grep 'const SchemaV1'`. **Unvalidated claim.** **Fix:** either add a real check (`Build`/`Diff`/`Emit` errors when `Schema != SchemaV1`) with a test, or re-disposition T-04-01 to deferred/Phase-5 and stop calling a bare const a mitigation.

### Notable MEDIUM (address where cheap; several cluster on CH-1/CH-5)
- Builder PATH split (`$HOME/bin:$PATH` → additions vs base marker) is an unvalidated Go-side string-parse; edge cases (mid-list base, no base marker, `${PATH}` brace form). Add a POC/EVIDENCE entry or narrow the builder to the router-admitted prepend/append shapes and route the rest imperative.
- NUL body-parser "slice up to next `\n##` marker" can be fooled by a body line starting `##`; bound the section by record-count/offset or a NUL-preceded sentinel, not a `\n##` scan.
- `ListDelta.Deletions` / `RebuildListFromBase.Deletions` are always empty this phase — note explicitly as validated-present-but-unexercised (SPEC Req 1 "additions+deletions" half-covered).
- Partial-apply / interrupted-switch failure mode unaddressed (plain functions, no transaction/rollback) — add a threat-register row + document the recovery contract (Phase 5 seam).
- Cross-terminal undo-slot re-capture on double-`checkout` overwrites the captured prior with already-applied state — specify a `${+slot}`-guarded capture-idempotency (only capture on clean base).
- Injection corpus not run through the slot-name derivation path (OQ-10/C24 name→slot) — add adversarial name cases.
- (simplicity) 13-type Op union and the self-contained "Hybrid helper-def preamble" (OQ-9) are heavier than SW-01/SW-02 require; pin OQ-9 to bare `zp_*` calls (the test supplies inline helpers); optionally collapse paired restore/unset ops. Not blocking.

### Confirmed sound (held up under attack)
`zquote` inert for value contexts (C5); verbatim function-body restore (C6); `${+name}` shadow guards (C1/OQ-8); `${(P)+var}` env drift guard where var holds the name (C2/C21); NUL-framed body dump (C14/C23); plain loader functions (C8); tri-state `*string`+omitempty (C15); two-type AliasSet/FuncSet split essential per C16.

**HIGH_COUNT = 16 → not converged. Proceed to replan (cycle 1 revision).**

## Cycle 2 (reviewing the cycle-1 revision)

Per-lens HIGH (return lines): correctness=3, risk=4, requirement-coverage=1, security=3, simplicity=0 → **HIGH_COUNT=11** (down from 16). All 8 cycle-1 fixes (CH-1..CH-8) verified landed and correct. New/second-order consensus HIGH (deduped → 7):

**CH-9 — CH-7 apply-side option capture is MISSING (strong consensus: risk, requirement-coverage, security).** CH-7 correctly moved `was_on` to runtime-captured and specified the DEACTIVATE side (`RestoreOption` reads the slot), but the APPLY per-op rendering enumeration (SetScalar/AddAlias/AddFunc have `${+slot}`-guarded capture rules) OMITS `SetOption` — nothing captures the live option state before `setopt`/`unsetopt`, so `RestoreOption` reads an unwritten slot → option restore silently fails (zero-residue violation on the options class). Also: NO EVIDENCE claim covers option capture/restore (no C21-analog for options). **Fix:** add a `SetOption` apply rule — `${+slot}`-guarded idempotent capture of live `[[ -o optname ]]` into a per-switch was_on slot BEFORE setopt/unsetopt; add a functional option drift/restore fixture in the residue test; add a pass-2 EVIDENCE claim proving live option capture/restore round-trips.

**CH-10 — full-env `${(@kv)parameters}` snapshot instrument is NOT self-stable + unvalidated (risk, security).** The CH-2 instrument iterates ALL parameters, including volatile specials (SECONDS, RANDOM, LINENO, funcstack, pipestatus, `_`) and the harness's own snapshot/loop vars — two identical snapshots differ → false-red, or an unaudited filter → false-green (re-opens the C19 blind spot CH-2 exists to close). No EVIDENCE entry proves the instrument is byte-stable. **Fix:** specify an AUDITED exclusion allowlist of volatile/read-only specials + harness vars (or snapshot only user-scope params via `typeset +`), capture via a fd/file not command-substitution; add a pass-2 POC proving self-stability (empty diff across two no-op snapshots) AND that the meta-assert leak cases (non-exported leak, exported value-only change) still fire.

**CH-11 — CH-6 functional/mutant test is non-discriminating (security).** C25 proved a SOURCE-LITERAL pattern over-matches, but the emitted loop uses a runtime VARIABLE `$target`; with GLOB_SUBST off (zsh default), `[[ $e == $target ]]` (unquoted) and `[[ $e == "$target" ]]` (quoted) behave IDENTICALLY as literal-equality — so the CH-6 functional test passes on BOTH the fix and the bug (non-discriminating). **Fix:** make a THIRD substitutable mutant emit `${path:#$target}` (the real C10 glob form, which DOES over-match a variable) and assert the residue test fails on it; correct the prose so quoting is documented as a GLOB_SUBST/robustness guard, not the sole barrier.

**CH-12 — internal contradiction: deactivate rebuild-to-base vs per-element removal loop (risk, security, correctness-adjacent).** CH-1c defined deactivate's list op as pure rebuild-to-base (`PATH="$ZP_BASE_PATH"`, no additions re-added, no per-element removal), but the plan ALSO mandates the quoted-RHS element-removal loop (CH-6) and cites C25 + the metacharacter fixture against it. In single-active v2.0, deactivate has no `$target` to remove — the element-removal loop is dead code. **Fix:** reconcile — state deactivate list reversal is full rebuild-to-base; scope the quoted-RHS element-removal to the path that actually compares elements (activate-side re-application / future deletion / multi-managed, currently unexercised like ListDelta.Deletions); change the metacharacter residue sub-check to assert base-restore DROPS `/opt/tool*` (a profile addition absent from base), not that a quoted comparison spared it.

**CH-13 — Added→RestoreShadowed derivation unstated (correctness).** Diff emits `RestoreShadowedAlias` per name in `active.Aliases.Added` (since `Shadowed` is never builder-populated per D-06; the runtime `${+slot}` guard is authoritative), but the plan never states this — an executor could iterate the always-empty `Shadowed` map → zero shadow-restore ops → silent SPEC Req 7 failure. **Fix:** state explicitly that deactivate emits paired `Unalias`+`RestoreShadowedAlias` (and Func analog) per name in `Added` (Shadowed not consulted at diff time; runtime `${+slot}` guard decides); add a diff test (populated Added + empty Shadowed → one restore op per added name).

**CH-14 — switch-ordering hazard in the random residue harness (correctness).** If the harness generates two applies without an intervening deactivate (A then B both shadow `ll`), B captures A's `ll` (not base's) → deactivate-B restores A's `ll` → residue vs base. **Fix:** specify the harness generates only BALANCED sequences (each apply matched by its deactivate before a different profile applies), or guard emit's apply for an already-active different profile; assert the generator never nests two applies without an intervening deactivate.

**CH-15 — base-ownership sub-check is a tautology (correctness).** The rescoped sub-check asserts `/usr/local/bin` (base + profile-added) survives "because rebuild-from-base restores base" — trivially true for ANY base entry regardless of whether the profile's addition was mishandled; it does NOT prove ownership-awareness. **Fix:** strengthen to assert `$#path` byte-identical to baseline AND `/usr/local/bin` appears EXACTLY once after apply→deactivate (guards both strip AND duplicate), with a negative control (a mutant that strips base entries must fail it).

**Also (LOW, cheap):** stale "C25/C26 UNVERIFIED — pass-2 must prove" wording lingers in both plans though EVIDENCE now records them PROVEN/STATIC-VALIDATED — clean it so the executor doesn't re-run done POCs.

**HIGH_COUNT = 11 → not converged (16→11, decreasing). Proceed to replan (cycle 2 revision).**

## Cycle 3 (reviewing the cycle-2 revision)

Per-lens HIGH (return lines): correctness=1, risk=1, requirement-coverage=0, security=2, simplicity=0 → **HIGH_COUNT=4** (16→11→4). All cycle-2 fixes (CH-9..CH-15) verified landed and correct; C27/C28 PROVEN. Three distinct new/second-order HIGH:

**CH-16 — type-class snapshot filter excludes the `aliases` AND `options` classes (false-green, 2 of 6 residue classes; consensus: correctness + risk).** On zsh 5.9 the `aliases` and `options` module-backed associations are typed `association-hide-hideval-special`, so the C28 type-class filter (skip `(*special*|*tied*|*hide*|undefined)`) EXCLUDES them. The instrument separately snapshots function BODIES + PATH, but NOT alias bodies or option state — yet the plan claims "the `$options` class is part of the byte-identical full snapshot." So a leaked alias or unrestored option passes byte-identical — a C19-class false-green contradicting SPEC Req 5 ("byte-identical `$aliases`/`$options` … no surviving prior-profile alias/function/option"). The targeted `ll`/`extendedglob` sub-checks only cover specific fixture names, not the general property. **Fix:** add dedicated, filter-INDEPENDENT snapshot sections for option state (iterate `${(@k)options}`, `[[ -o $opt ]]` / `${options[$k]}`) and alias bodies (iterate `${(@k)aliases}`/`${aliases[$k]}`, like function bodies), captured deterministically (sorted) in BOTH snapshots so they're byte-comparable without the filter dropping them; add C28-analog meta-asserts (an injected option-drift AND an injected alias-body-change must each fire the diff); correct the false "options in full snapshot" claim. Also (MEDIUM, fold in): add `zmodload zsh/parameter` to the harness preamble and assert a known user scalar appears in baseline (proves the map is populated, not silently empty → all-classes false-green).

**CH-17 — `SetOption` emits the option NAME into unquoted command positions: new injection surface (security).** The CH-9 fix emits `optname` (← `OptionSet.Name` ← parser word-literals of a `setopt`/`unsetopt` line = user-controlled) into `[[ -o optname ]]`, `setopt optname`, `unsetopt optname`, and the was_on slot-name derivation — unquoted, unsanitized. The T-01-06 injectable-NAME enumeration omits the option name; the injection/slot-name corpus never runs SetOption; C27 used only well-formed names. New double-eval EoP surface with no evidence. **Fix:** validate `OptionSet.Name` against the bare-identifier grammar `^[A-Za-z_][A-Za-z0-9_]*$` before emitting (drop/no-part on failure); add the option name to the adversarial NAME corpus and assert no canary fires through SetOption; add the option name to the T-01-06 trust-boundary list; add a pass-3 EVIDENCE claim (C29) proving a hostile option name is inert or rejected.

**CH-18 — stale/contradictory revision cruft, incl. a `<done>` acceptance block re-asserting the REFUTED CH-6 mechanism (security + requirement-coverage + simplicity).** The plan BODY correctly encodes CH-11/CH-12 (deactivate = full rebuild-to-base; quoted-RHS reserved/unexercised), but: the Task-1 `<done>` block still says deactivate is "ownership-aware (QUOTED-RHS literal-equality PATH rebuild-from-base, CH-6)"; the verification block (line ~282) reproduces the "CH-6 quoted-RHS present" gate without the reserved/comment qualifier; the validated_ground header (line ~64) still names the REFUTED "audited volatile-param allowlist" as the CH-10 mechanism; and C27/C28 are labelled "NEW UNVERIFIED — pass-2 must prove" in ~5 places though EVIDENCE (and the same file elsewhere) records both PROVEN. An executor reading `<done>`/headers as the acceptance summary could emit the dead/glob-hazardous per-element loop or re-run finished POCs. **Fix:** rewrite the `<done>` line + verification label to the CH-11/CH-12 wording (full rebuild-to-base; quoted-RHS reserved-in-comment); change the validated_ground CH-10 mechanism to "type-class filter"; relabel every C27/C28 "NEW UNVERIFIED — pass-2 must prove" → "PROVEN".

**HIGH_COUNT = 4 → not converged (16→11→4, decreasing). Proceed to replan (cycle 3 revision).**
