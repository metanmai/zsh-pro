## Details

Only REFUTED claims are detailed below (PROVEN claims are locked as-stated per the table).

### C1 — `${(P)+var}` set-test for a literal slot name
- **Claim:** `${(P)+var}==1` iff the parameter named by `$var` is SET (incl. empty), 0 if unset — used to test whether a literal-named slot is set.
- **What actually happened:** `zsh -f -c 'FOO=bar; print ${(P)+FOO}'` printed `0`, not `1`. `(P)` indirects through the VALUE of `FOO` (`bar`), testing a parameter literally named `bar` (which does not exist). The stated semantic is correct, but the reproduction recipe conflated `${(P)+FOO}` with `${+FOO}`.
- **Correct fact:** To set-test a LITERAL-named slot, use `${+FOO}` (no `(P)`): unset→0, set-including-empty→1. `(P)` is correct ONLY when the slot NAME is stored in another variable (`name=FOO; ${(P)+name}`). The `-n`-cannot-distinguish-unset-from-empty half is independently confirmed.
- **Action taken:** Replaced every `${(P)+literalName}` set-test in the shadow-restore / env-drift guard guidance with `${+name}` (no P) across 04-RESEARCH.md (Pitfall 4, Don't Hand-Roll, State-of-the-Art, appendix), 04-CONTEXT.md (D-12), 04-OPEN-QUESTIONS.md (OQ-8), and 04-SPEC.md. Retained `(P)` only for the env path where the operand IS a var holding the name (C21, confirmed correct there).

### C4 — corrected cycle byte-identical vs Phase-1 snippet leak
- **Claim:** The corrected `${+name}` cycle is byte-identical; "the faithful Phase-1-snippet reproduction leaks a residual `ll` alias."
- **What actually happened:** The corrected `${+name}` full cycle IS byte-identical (proven). But the actual Phase-1 loader snippet restores a shadowed `ll` with a scalar `[[ -n "$PRIOR" ]]` test (no `(P)`), which is zero-residue for a non-empty `ll`. It leaks only for an EMPTY prior body, and the residue is the prior being DROPPED (unset) — an ABSENCE, not a surviving alias.
- **Correct fact:** A `${(P)+literalName}` guard fails to restore the shadow (leaves it UNSET); the `-n` scalar guard additionally drops an empty-body prior. Neither leaves a residual alias behind.
- **Action taken:** Reworded the C4-derived characterization in 04-RESEARCH (§1 risk 2, State-of-the-Art) to describe the failure as a DROPPED prior (empty-body case for `-n`; wrong-parameter no-op for `(P)+literal`), not a surviving/residual alias. Design decision (use `${+name}`) unchanged.

### C6 — zquote across all three value contexts (function bodies)
- **Claim:** zquote is injection-safe under double-eval across scalar, alias, AND `functions[name]=<body>` contexts, "so re-parsing still yields an inert literal."
- **What actually happened:** `eval "functions[fv]='x; touch CF'"; fv` fired the canary — a function BODY is executable code by nature; wrapping it in single quotes only makes the edge bytes literal, the body still runs on call. An adversarial single-quote payload produces "invalid function definition"/"unmatched '". Scalar and alias contexts are inert as claimed.
- **Correct fact:** Function restore is verbatim capture-and-reassign (`functions[name]=$capturedBody`), where the body round-trips as DATA via the NUL-delimited capture (C14); you cannot make a function body an inert literal with zquote. The static-quote/dynamic-verbatim split (OQ-6) applies to scalar/alias VALUE contexts only, not to function-body reassignment.
- **Action taken:** Scoped the zquote-inert guarantee to scalar-export and alias-body contexts in 04-RESEARCH (§4 injection table + threat text, Don't Hand-Roll, Security Domain) and 04-CONTEXT (D-13); documented function-body restore as verbatim capture. Noted the correction in 04-OPEN-QUESTIONS OQ-6.

### C7 — emit.go / regen.go relationship and the Dynamic-keyed split
- **Claim:** The static-vs-dynamic split is keyed strictly on the op's `Dynamic` bool; behaviorally the same value verbatim expands and zquote'd stays literal.
- **What actually happened:** The behavioral surface holds, but (1) there is no `emit.go` yet, and (2) the existing `Provider.Regenerate` (core/shell/zsh/regen.go, delegated from core/ir/regen.go) emits the captured `Value` VERBATIM in every branch and never reads any `Dynamic` bool — grep for a Dynamic-keyed quoting branch in production emission returns nothing. Two `model.Entry` values with identical `Value="$HOME/go"` but opposite `Dynamic` produced byte-identical output. The static case stays literal because the surrounding single-quotes were captured as part of `Value` (verbatim source-span capture), not because emission zquotes on Dynamic.
- **Correct fact:** `core/shell/zsh/emit.go` is a NEW file for ACTIVATION codegen (apply/deactivate plans), distinct in purpose from the existing ingest-regeneration `regen.go`. The Dynamic-keyed static-literal-vs-dynamic-verbatim split is NEW behavior emit.go must implement — it is NOT provided by existing regen infrastructure.
- **Action taken:** Corrected 04-RESEARCH (§4 static-vs-dynamic, Architectural Responsibility Map, State-of-the-Art) and 04-CONTEXT (D-13, code_context) to state emit.go is new/distinct and the split is new behavior; removed wording implying existing code already keys emission on Dynamic. Noted in 04-OPEN-QUESTIONS OQ-6.

### C10 — literal PATH element deletion
- **Claim:** `${path:#/opt/x}` removes exactly the matching element cleanly, enabling ownership-aware deletion.
- **What actually happened:** `${path:#PATTERN}` is GLOB/pattern subtraction, not literal-equality. `${path:#/opt/tool?}` against `(… /opt/toolX /opt/toolY …)` deleted the siblings `/opt/toolX` and `/opt/toolY` (5→2). `*` and `[…]` over-match the same way. Metacharacter-free paths delete cleanly, but a PATH element legally containing `? * [ ]` causes collateral deletion.
- **Correct fact:** Ownership-aware PATH element removal must use LITERAL-equality matching (rebuild the array comparing each element with `[[ $e == $target ]]` string-equality, or otherwise disable pattern semantics), NOT `${path:#pattern}`.
- **Action taken:** Corrected 04-RESEARCH (Req 6 op vocabulary / §3, Don't Hand-Roll PATH row, appendix POC-Z6c) to mandate literal-equality element removal. Noted in 04-OPEN-QUESTIONS OQ-12.

### C11 — ownership-aware PATH restore under `typeset -U`
- **Claim:** Deactivating one profile that added `/usr/local/bin` must not remove it when another active profile (or the base) also has it; restore removes only entries this profile added vs the base.
- **What actually happened:** The prover's "remove one occurrence per addition" (string-subtraction) algorithm satisfies the claim ONLY without `typeset -U path`. With `typeset -U` active — mandated by the project's own PATH-no-growth research — co-owned entries collapse to a single physical entry, so removing "one occurrence per addition" strips the shared entry another active profile still needs (`/usr/local/bin` gone while B is active). Repeated cycles without dedup also erode base-owned entries.
- **Correct fact:** Ownership-aware PATH restore needs a reference-count or set-based ownership model (only remove an entry when NO other active profile/base owns it) that is correct under dedup — not naive per-addition string subtraction. Rebuild-from-base + re-apply other actives satisfies the claim; per-addition subtraction does not.
- **Action taken:** Corrected 04-RESEARCH (§3 PATH ownership discussion, Req 6 row, Risks/Landmines) to require a dedup-correct ownership model. Noted as a material design correction in 04-OPEN-QUESTIONS OQ-12.

### C12 — `${functions[name]}` leading-tab-on-each-line invariant
- **Claim:** `${functions[name]}` returns the body without the wrapper, WITH a leading tab on each line, no trailing newline; reassign is byte-identical.
- **What actually happened:** The basic round-trip holds (`ff(){ echo hi }` → 8 bytes `\techo hi`, no trailing newline; capture-reassign byte-identical, stable across cycles). But a body containing a heredoc does NOT tab-prefix every line — heredoc content and terminator lines have no leading tab. "Leading tab on each line" is a false universal.
- **Correct fact:** The body has no trailing newline and round-trips byte-identically via capture-reassign; the per-line leading-tab claim holds only for lines outside heredoc bodies. Do not rely on a universal leading-tab invariant.
- **Action taken:** Dropped "leading tab per line" as a universal invariant in 04-RESEARCH (§5 body-format facts, appendix POC-Z1a); kept the no-trailing-newline + byte-identical-reassign facts.

### C14 — NUL-delimited encoding justification
- **Claim:** NUL-delimited `print -rN` records round-trip a multi-line body byte-for-byte "because a zsh C-string value can never contain NUL."
- **What actually happened:** Both operational halves confirmed (naive tab dump splits a multi-line record; NUL form round-trips byte-for-byte). But the justification is false: on zsh 5.9 an arbitrary scalar value CAN hold a literal NUL (`v=$'a\0b'` → `${#v}`=3; a Go 0x00 splitter then sees an extra field). The narrower true reason the round-trip is safe: FUNCTION BODIES specifically get reparsed, so `${functions[name]}` never carries a raw 0x00.
- **Correct fact:** Keep the NUL-delimited encoding (operationally confirmed). The safety rests on function bodies being reparsed (no 0x00 in a body), not on the overbroad "a zsh string can never contain NUL."
- **Action taken:** Softened the justification in 04-RESEARCH (§5 encoding fork + appendix POC-Go-RT, Don't Hand-Roll) to the function-body-reparse reason; removed the "a zsh C-string can never contain NUL" universal.

### C15 — `*string`+omitempty as the "only" tri-state shape
- **Claim:** `*string` with `json:"original,omitempty"` is the ONLY shape distinguishing unset/empty/value.
- **What actually happened:** The tri-state marshal/unmarshal behavior is confirmed lossless (nil→key omitted, &""→`""`, &"vim"→`"vim"`; a plain string conflates unset and empty). But "only" is false — a compiled counterexample showed `json.RawMessage` with `omitempty`, and a `*struct{V string}` / custom `json.Marshaler` with a present-flag, also distinguish all three.
- **Correct fact:** `*string`+omitempty is the simplest/recommended shape for the tri-state, not the only one. The tri-state behavior stands.
- **Action taken:** Changed "the only Go shape that distinguishes all three states" to "the simplest/recommended shape" in 04-RESEARCH (§2 tri-state, appendix POC-J1). (D-02 in CONTEXT already reads "single load-bearing type CHOICE"; left as the design choice, which is defensible.)

### C19 — property test snapshots names, not bodies
- **Claim:** The zero-residue property test yields a byte-identical six-class snapshot diff and genuinely detects residue; a mutated append-PATH emitter fails it.
- **What actually happened:** The PATH mechanism is real (correct emitter passes with stable `$#path`; the append mutation fails). But the snapshot instrument silently MISSES two residue classes: the functions class emits `${(ok)functions}` (NAMES only), so a redefined-but-not-restored function BODY passes as byte-identical; the env class uses `typeset -x` (EXPORTED only), so a leaked non-exported shell var is invisible.
- **Correct fact:** The property test must snapshot function BODIES (and all six classes fully — exported and non-exported env), or body-level and non-exported residue passes silently. Detecting residue "in general" requires body-level snapshots, not just names + one PATH mutation.
- **Action taken:** Corrected the SW-02 / §6 test-harness description in 04-RESEARCH (§6 structure + the snapshot-class enumeration) to require function-body and full-class snapshotting. Aligns with the six-class byte-identical criterion already in 04-SPEC Req 5 (no SPEC edit needed — the SPEC does not encode the names-only mechanism).

### C22 — "core/activate contains NO zsh token" grep
- **Claim:** A grep finds no `unalias `/`unset -f`/`setopt `/`export `/`alias ` string literal in `core/activate` (only Go type names like `Unalias`).
- **What actually happened:** `core/activate` does not exist yet. Reconstructing the op vocabulary showed the claim's naive grep both false-matches Go identifiers AND names forward tokens (`alias`/`export`/`setopt`/`unsetopt`) that regen.go legitimately emits today — a naive tree grep for those would false-positive on regen.go.
- **Correct fact:** The invariant needs a PRECISE check: case-sensitive, word-boundary (`\bunalias\b`, `\bunset -f`), scoped to genuinely reverse tokens (`unalias`/`unset -f`), excluding Go identifier type names (`Unalias`, `SetOption`) and comments. `alias`/`export`/`setopt`/`unsetopt` are forward-emitted by regen.go and must be allowed there.
- **Action taken:** Refined the token-free acceptance wording in 04-RESEARCH (§3 token-free acceptance, Risks/Landmines #8) to state the check precisely (case-sensitive, word-boundary, reverse-token-scoped, excluding Go type names/comments). Design decision (core/activate stays token-free) unchanged.

### C23 — body-dump section framing must be multi-line-safe
- **Claim:** Extending `introspectScript` with body-dump sections is additive and non-breaking (name maps untouched, analyze reads only Available, zsh-absent→Available:false).
- **What actually happened:** The additive sub-claims are CONFIRMED against real code: `IdentitySet` name maps are `map[string]bool` (untouched), `analyzer.go:84` reads only `ids.Available`, zsh-absent/error returns `IdentitySet{Available:false}`, and all IdentitySet literals are keyed. But reusing the existing LINE-ORIENTED `##DELIMITER##` framing (`parseIntrospect` does `strings.Split(s,"\n")` + a full-line switch on `##…##`) for `##ALIASBODIES##`/`##FUNCTIONBODIES##` breaks: multi-line function bodies truncate (continuation lines lack `" -> "`), and a heredoc body emitting an unindented `##PATH##`-like line is misread as a section switch, corrupting every following section.
- **Correct fact:** Body-dump sections must use a multi-line-safe encoding (NUL-delimited or length-prefixed, consistent with C14), and the parser for those sections must NOT be the existing line reader. The narrow additive sub-claims (name maps untouched, analyze reads only Available, zsh-absent→Available:false) stay confirmed.
- **Action taken:** Corrected 04-RESEARCH (§5 additive extension + section-boundary caveat) to require multi-line-safe framing and a dedicated (non-line) body parser, and to keep the confirmed additive sub-claims. Noted in 04-OPEN-QUESTIONS OQ-12.
