### C1 — `${(P)+var}` set-test for a literal slot name
- **Claim:** `${(P)+var}==1` iff the parameter named by `$var` is SET (incl. empty), 0 if unset — used to test whether a literal-named slot is set.
- **What actually happened:** `zsh -f -c 'FOO=bar; print ${(P)+FOO}'` printed `0`, not `1`. `(P)` indirects through the VALUE of `FOO` (`bar`), testing a parameter literally named `bar` (which does not exist). The stated semantic is correct, but the reproduction recipe conflated `${(P)+FOO}` with `${+FOO}`.
- **Correct fact:** To set-test a LITERAL-named slot, use `${+FOO}` (no `(P)`): unset→0, set-including-empty→1. `(P)` is correct ONLY when the slot NAME is stored in another variable (`name=FOO; ${(P)+name}`). The `-n`-cannot-distinguish-unset-from-empty half is independently confirmed.
- **Action taken:** Replaced every `${(P)+literalName}` set-test in the shadow-restore / env-drift guard guidance with `${+name}` (no P) across 04-RESEARCH.md (Pitfall 4, Don't Hand-Roll, State-of-the-Art, appendix), 04-CONTEXT.md (D-12), 04-OPEN-QUESTIONS.md (OQ-8), and 04-SPEC.md. Retained `(P)` only for the env path where the operand IS a var holding the name (C21, confirmed correct there).

### C4 — corrected cycle byte-identical vs Phase-1 snippet leak
- **Claim:** The corrected `${+name}` cycle is byte-identical; "the faithful Phase-1-snippet reproduction leaks a residual `ll` alias."
- **What actually happened:** The corrected `${+name}` full cycle IS byte-identical (proven). But the actual Phase-1 loader snippet restores a shadowed `ll` with a scalar `[[ -n "$PRIOR" ]]` test (no `(P)`), which is zero-residue for a non-empty `ll`. It leaks only for an EMPTY prior body, and the residue is the prior being DROPPED (unset) — an ABSENCE, not a surviving alias.
- **Correct fact:** A `${(P)+literalName}` guard fails to restore the shadow (leaves it UNSET); the `-n` scalar guard additionally drops an empty-body prior. Neither leaves a residual alias behind.
- **Action taken:** Reworded the C4-derived characterization in 04-RESEARCH (§1 risk 2, State-of-the-Art) to describe the failure as a DROPPED prior (empty-body case for `-n`; wrong-parameter no-op for `(P)+literal`), not a surviving/residual alias. Design decision (use `${+name}`) unchanged.

### C6 — zquote across all three value contexts (function bodies)
- **Claim:** zquote is injection-safe under double-eval across scalar, alias, AND `functions[name]=<body>` contexts, "so re-parsing still yields an inert literal."
- **What actually happened:** `eval "functions[fv]='x; touch CF'"; fv` fired the canary — a function BODY is executable code by nature; wrapping it in single quotes only makes the edge bytes literal, the body still runs on call. An adversarial single-quote payload produces "invalid function definition"/"unmatched '". Scalar and alias contexts are inert as claimed.
- **Correct fact:** Function restore is verbatim capture-and-reassign (`functions[name]=$capturedBody`), where the body round-trips as DATA via the NUL-delimited capture (C14); you cannot make a function body an inert literal with zquote. The static-quote/dynamic-verbatim split (OQ-6) applies to scalar/alias VALUE contexts only, not to function-body reassignment.
- **Action taken:** Scoped the zquote-inert guarantee to scalar-export and alias-body contexts in 04-RESEARCH (§4 injection table + threat text, Don't Hand-Roll, Security Domain) and 04-CONTEXT (D-13); documented function-body restore as verbatim capture. Noted the correction in 04-OPEN-QUESTIONS OQ-6.

### C7 — emit.go / regen.go relationship and the Dynamic-keyed split
- **Claim:** The static-vs-dynamic split is keyed strictly on the op's `Dynamic` bool; behaviorally the same value verbatim expands and zquote'd stays literal.
- **What actually happened:** The behavioral surface holds, but (1) there is no `emit.go` yet, and (2) the existing `Provider.Regenerate` (core/shell/zsh/regen.go, delegated from core/ir/regen.go) emits the captured `Value` VERBATIM in every branch and never reads any `Dynamic` bool — grep for a Dynamic-keyed quoting branch in production emission returns nothing. Two `model.Entry` values with identical `Value="$HOME/go"` but opposite `Dynamic` produced byte-identical output. The static case stays literal because the surrounding single-quotes were captured as part of `Value` (verbatim source-span capture), not because emission zquotes on Dynamic.
- **Correct fact:** `core/shell/zsh/emit.go` is a NEW file for ACTIVATION codegen (apply/deactivate plans), distinct in purpose from the existing ingest-regeneration `regen.go`. The Dynamic-keyed static-literal-vs-dynamic-verbatim split is NEW behavior emit.go must implement — it is NOT provided by existing regen infrastructure.
- **Action taken:** Corrected 04-RESEARCH (§4 static-vs-dynamic, Architectural Responsibility Map, State-of-the-Art) and 04-CONTEXT (D-13, code_context) to state emit.go is new/distinct and the split is new behavior; removed wording implying existing code already keys emission on Dynamic. Noted in 04-OPEN-QUESTIONS OQ-6.

### C10 — literal PATH element deletion
- **Claim:** `${path:#/opt/x}` removes exactly the matching element cleanly, enabling ownership-aware deletion.
- **What actually happened:** `${path:#PATTERN}` is GLOB/pattern subtraction, not literal-equality. `${path:#/opt/tool?}` against `(… /opt/toolX /opt/toolY …)` deleted the siblings `/opt/toolX` and `/opt/toolY` (5→2). `*` and `[…]` over-match the same way. Metacharacter-free paths delete cleanly, but a PATH element legally containing `? * [ ]` causes collateral deletion.
- **Correct fact:** Ownership-aware PATH element removal must use LITERAL-equality matching (rebuild the array comparing each element with a QUOTED-RHS `[[ $e == "$target" ]]` string-equality, or otherwise disable pattern semantics), NOT `${path:#pattern}`. **REVIEWS CH-6:** an UNQUOTED RHS `[[ $e == $target ]]` is ALSO glob-matched (reintroduces this bug) — the RHS must be quoted; the quoted form is UNVERIFIED (C25, pass-2).
- **Action taken:** Corrected 04-RESEARCH (Req 6 op vocabulary / §3, Don't Hand-Roll PATH row, appendix POC-Z6c) to mandate literal-equality element removal. Noted in 04-OPEN-QUESTIONS OQ-12. Quoted-RHS requirement added via C25 (UNVERIFIED) and Plan 04-02 CH-6 handling.

### C11 — ownership-aware PATH restore under `typeset -U`
- **Claim:** Deactivating one profile that added `/usr/local/bin` must not remove it when another active profile (or the base) also has it; restore removes only entries this profile added vs the base.
- **What actually happened:** The prover's "remove one occurrence per addition" (string-subtraction) algorithm satisfies the claim ONLY without `typeset -U path`. With `typeset -U` active — mandated by the project's own PATH-no-growth research — co-owned entries collapse to a single physical entry, so removing "one occurrence per addition" strips the shared entry another active profile still needs (`/usr/local/bin` gone while B is active). Repeated cycles without dedup also erode base-owned entries.
- **Correct fact:** Ownership-aware PATH restore needs a reference-count or set-based ownership model (only remove an entry when NO other active profile/base owns it) that is correct under dedup — not naive per-addition string subtraction. ### C25 — quoted-RHS `[[ $e == "$target" ]]` is literal-equality (pass-2 PROVEN)
- **Claim:** In zsh, a QUOTED RHS in `[[ $e == "$target" ]]` disables glob/pattern matching and performs literal string-equality, so a PATH element containing glob metacharacters (`* ? [ ]`) is compared byte-literally and does NOT over-match siblings — the fix for the C10 collateral-deletion bug. An UNQUOTED RHS (`[[ $e == $target ]]`) pattern-matches (reintroduces C10).
- **POC:** `/tmp/gsd-docs-poc/04b/C25/poc.zsh`, run `zsh -f poc.zsh` under `zsh 5.9 (arm64-apple-darwin25.0)` (throwaway, not committed).
- **Observed:**
  - (a) unquoted `[[ /opt/toolX == /opt/tool? ]]` → **MATCH** (glob over-match — this is the C10 bug).
  - (b) quoted `[[ /opt/toolX == "/opt/tool?" ]]` → **no-match** (literal — correct).
  - (c1) rebuild loop `path=(/opt/toolX /opt/toolY '/opt/tool?' /usr/bin); target='/opt/tool?'; for e in $path; do [[ $e == "$target" ]] || newpath+=("$e"); done` → `out: /opt/toolX /opt/toolY /usr/bin` — removed ONLY the literal `/opt/tool?`, siblings intact.
  - (c2) same loop, `target='/opt/*'` (path holds `/opt/*` + `/opt/toolX/Y`) → siblings intact, only `/opt/*` removed.
  - (c3) same loop, `target='/opt/tool[ab]'` (path holds `/opt/tool[ab]` + `/opt/toola` + `/opt/toolb`) → `out: /opt/toola /opt/toolb /usr/bin` — only the literal `[ab]` element removed.
  - (c4) CONTROL with UNQUOTED RHS `[[ $e == $target ]]`, `target='/opt/tool?'` → `out: /opt/toolX /opt/toolY /usr/bin` — over-deleted the `?`-sibling `/opt/tool?`... note it deleted the literal `/opt/tool?` element itself here because `?` matches a single char; the operative C10 demonstration is (a) where `/opt/toolX` (a sibling) MATCHES the pattern `/opt/tool?`. Quoted (b/c) never over-matches; unquoted (a) does.
- **Verdict:** PROVEN. Quoted RHS is literal-equality in all metacharacter cases (`? * [ ]`); the rebuild-from-base loop with quoted RHS removes exactly the target element with zero collateral. Plan 04-02 Task 1's mandated `[[ $e == "$target" ]]` form (CH-6, threat T-04-13) is correct as written. No plan correction needed.
- **Note (harness artifact, not a claim issue):** an unquoted `path=(/opt/tool?)` ARRAY LITERAL under `errexit` triggers filename generation at assignment time (`no matches found`); the POC quotes the metacharacter array elements and sets `noglob` to isolate the `[[ ]]` comparison — this is a test-authoring detail, orthogonal to the claim. The emit.go loop iterates an already-populated `$path`, so it is unaffected.
