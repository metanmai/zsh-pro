## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** `profile.json` is the authoritative, lossless serialization of `model.Profile`. Every derived field — `ManagedOverride`, static/dynamic tag, category, declarative/imperative verdict, verbatim `Block.Text` — must survive serialization. JSON is the only candidate that preserves them without re-running the parser/classifier, so the store stays shell-agnostic (no re-parse on `Read`). (Rejected: per-category `.zsh`-only and single source-ordered `.zsh`-only — both lose derived fields unless the store re-parses, coupling it to a parser.)
- **D-02:** Commit a single source-ordered `profile.zsh` alongside the JSON, for human browsing and meaningful diffs. It is a **derived view** (JSON authoritative); generated by **reusing Phase 2's `core/shell/zsh/regen.go`** in source order. No new emit code; per-category emit stays Phase 4. (Rejected: per-category `.zsh` now.)
- **D-03:** `.zsh` emission goes through an **injected regenerator seam**, not a direct import. `core/store` stays shell-agnostic and must not import `core/shell/zsh`; the regenerator is injected at the composition root (mirroring `shell.Provider`). Exact seam shape is Claude's discretion.
- **D-04:** Store repo lives at `$XDG_DATA_HOME/zsh-pro` (default `~/.local/share/zsh-pro`), overridable via `$ZSHPRO_HOME`. XDG_DATA_HOME is the correct spec location (a git store is data, not user-edited config).
- **D-05:** Default/baseline git branch is `main`; it holds the (eventually) ingested `~/.zshrc`. `create <name>` forks `main` (every profile shares a clean common ancestor). (Rejected: forking the current profile.)
- **D-06:** `Init` is idempotent and never clobbers an existing repo. Re-running `Init` is a safe no-op. Absent `git` degrades with a clear, zsh-pro-phrased error — never a crash, never a raw git error.
- **D-07:** Secrets become late-bound **pointers**, not dropped values — consistent with EVAL-01. The committed profile stores a reference; the literal value never enters the git tree.
- **D-08:** Distinguish literal vs already-dynamic secrets. A secret-named var whose value is **already dynamic** (e.g. `export TOKEN=$(op read ...)`) is **committed verbatim** (already a pointer). Only **literal** secrets (`export API_KEY="sk-abc123"`) are converted to a `SecretRef`.
- **D-09:** `SecretRef` is a resolver-agnostic pointer serialized into the Profile now. Shape: `kind:key` (e.g. `keychain:API_KEY`, `file:API_KEY`, `cmd:'op read ...'`). Default backend = **OS keychain via subprocess** (`security` macOS / `secret-tool` Linux — no plaintext on disk, no new dependency), with a **git-ignored vault file** fallback. Future managers slot in as new `kind`s.
- **D-10:** Phase 3 builds full exclusion (not just a hook). On `Commit`, literal secrets are detected (reusing the shipped detector), captured into the resolver backend, replaced by a `SecretRef`, and a **withheld-report** (name + source line) is returned. The deref side (reading the value back, setting/unsetting the env var) is Phase 4/5.
- **D-11:** Git is fully abstracted behind zsh-pro verbs — the user never touches raw git. All operations wrapped by `zsh-pro` commands; all errors phrased in zsh-pro terms.
- **D-12:** Read profiles via `git show <branch>:<path>` from the object DB — never a user-facing checkout. `Commit` writes to a target branch via plumbing (temp index / `commit-tree` + `update-ref`) so one terminal's commit never disturbs another's. (Rejected: git worktree per terminal; plain `git checkout` of a shared HEAD.)
- **D-13:** Active profile tracked per-terminal in an env var carrying the profile **name only** (e.g. `ZSHPRO_PROFILE=work`). Repo path derives from `$ZSHPRO_HOME`/XDG. `Current()` reads the env var; **unset ⇒ `main`** implicitly.

## Summary

Phase 3 is a thin, well-bounded Go package (`core/store`) that drives the `git` binary as a subprocess — exactly mirroring the existing `zsh -f` pattern in `core/shell/zsh/introspect.go` (`exec.CommandContext` + timeout + graceful-degrade). The two genuinely subtle pieces are (1) committing to a branch **without** disturbing any working tree or other terminal (D-12), and (2) keychain-via-subprocess secret capture (D-09/D-10). Both were verified hands-on on this machine.

The single most important verified finding: **use a bare repository** (`git init --bare`) at `$ZSHPRO_HOME`. A bare repo has *no working tree and no checked-out HEAD*, which dissolves the entire class of "my commit changed another terminal's working tree" problems that D-12 is fighting. Every profile branch is created and updated purely in the object database via plumbing (`hash-object -w` → temp-index `write-tree` → `commit-tree` → `update-ref`), and every read is `git show <branch>:<path>` (or `cat-file`). There is no `git checkout` anywhere in the store, ever — which is exactly what D-11/D-12 demand. (I verified the non-bare alternative — a dedicated internal orphan HEAD branch — also works, but it is strictly more fragile: a non-bare repo with `update-ref` on the HEAD branch leaves the working tree showing phantom `D`eletions. Bare avoids this entirely.)

For serialization (D-01), the Phase 2 `model.Profile`/`Entry` types are already cleanly JSON-serializable: all fields are exported, the only enum (`ManagedOverride`) is a string, and there is no unexported state. Go's `encoding/json` is deterministic (struct fields in declaration order; map keys sorted) so a byte-stable round-trip is achievable with `json.MarshalIndent` + a trailing newline. `SecretRef` is a new `core/model` type; it must slot into `Entry` additively (a new field) so the Phase 2 round-trip oracle is not regressed.

**Primary recommendation:** Build `core/store` as a bare-repo git driver. Init = `git init --bare -b main` + an empty-tree root commit on `main` if absent (idempotent). Commit = plumbing-to-branch (recipe below) writing `profile.json` (authoritative) + `profile.zsh` (derived via the injected regenerator seam) + a git-ignored handling of literal secrets converted to `SecretRef`. Read = `git show <branch>:profile.json` → `json.Unmarshal`. Branches = `git for-each-ref`. Current = read `ZSHPRO_PROFILE` (unset ⇒ `main`). Secrets = reuse `secretRe`, capture literals to keychain via `security`/`secret-tool`, return a withheld-report. Every git/keychain call mirrors the `introspect.go` subprocess shape and degrades cleanly when the binary is absent.

### Pattern 1: Commit to a branch without a working tree (the heart of D-12)
**What:** Build a tree in an *isolated* temp index, make a commit object parented on the branch's current tip (or a root commit for a brand-new branch), and move the ref — all in the object DB. No checkout, no working-tree mutation.
**When to use:** Every `Commit`. This is the load-bearing recipe.
**Verified recipe** (run hands-on on this machine, git 2.50.1, against a **bare** repo):
```bash
# Pre: repo is bare at $GIT_DIR. Use a temp index file OUTSIDE any working tree.
TMP_INDEX="$(mktemp)"   # in Go: os.CreateTemp; pass via env GIT_INDEX_FILE=...

# 1. Write each file's content as a blob (content via stdin — never touches disk in the repo).
BLOB_JSON=$(printf '%s' "$jsonBytes" | git hash-object -w --stdin)
BLOB_ZSH=$(printf '%s' "$zshBytes"  | git hash-object -w --stdin)

# 2. Seed the temp index from the branch's current tree IF the branch exists; else start empty.
if git cat-file -e "refs/heads/$BRANCH" 2>/dev/null; then
  GIT_INDEX_FILE="$TMP_INDEX" git read-tree "$BRANCH"
  PARENT_ARGS=(-p "$(git rev-parse "$BRANCH")")
else
  GIT_INDEX_FILE="$TMP_INDEX" git read-tree --empty
  PARENT_ARGS=()   # root commit for a brand-new branch
fi

# 3. Stage the blobs into the temp index (cacheinfo = mode,sha,path; no file on disk needed).
GIT_INDEX_FILE="$TMP_INDEX" git update-index --add --cacheinfo 100644,"$BLOB_JSON",profile.json
GIT_INDEX_FILE="$TMP_INDEX" git update-index --add --cacheinfo 100644,"$BLOB_ZSH",profile.zsh

# 4. Snapshot the temp index to a tree object.
TREE=$(GIT_INDEX_FILE="$TMP_INDEX" git write-tree)

# 5. Create the commit object (message via stdin; deterministic author/committer set via env — see gotcha).
COMMIT=$(printf '%s' "$msg" | git commit-tree "$TREE" "${PARENT_ARGS[@]}")

# 6. Atomically move the branch ref.
git update-ref "refs/heads/$BRANCH" "$COMMIT"

rm -f "$TMP_INDEX"
```
In Go, set `cmd.Env = append(os.Environ(), "GIT_INDEX_FILE="+tmpIndexPath, "GIT_DIR="+repoPath, ...)` and capture stdout for the object SHAs.

**Gotchas (verified / documented):**
- **Use `git init --bare`.** [VERIFIED] On a *non-bare* repo, `update-ref refs/heads/main` to a commit containing `profile.json` while the working tree lacks that file makes `git status` report `D profile.json` — a phantom deletion that would confuse any later git interaction. A bare repo has no working tree, so this is impossible. (`git status` in a bare repo errors with `fatal: this operation must be run in a work tree` — the store never calls it.)
- **Put `GIT_INDEX_FILE` outside any working tree** (e.g. `os.CreateTemp("", ...)`), and delete it after. In a bare repo there is no working tree to pollute, but still clean it up.
- **First commit / empty repo:** for a brand-new branch, omit `-p` (root commit). [VERIFIED] `commit-tree <tree>` with no `-p` produces a valid root commit.
- **Deterministic commits (for byte-stable history in tests):** set `GIT_AUTHOR_NAME/EMAIL/DATE` and `GIT_COMMITTER_NAME/EMAIL/DATE` in `cmd.Env`. Without them git reads user config / wall-clock time, which makes commit SHAs non-reproducible. [CITED: git-commit-tree(1) env vars]
- **`GIT_DIR` vs `GIT_WORK_TREE`:** for a bare repo only `GIT_DIR` (the repo path) matters; never set `GIT_WORK_TREE` (it would re-introduce a working tree). The store passes `GIT_DIR=$ZSHPRO_HOME` (or `git -C $ZSHPRO_HOME ...`) and nothing else.
- **`--cacheinfo` mode:** `100644` = normal file. Both `profile.json` and `profile.zsh` are normal files. The empty-tree SHA constant (if ever needed) is `4b825dc642cb6eb9a060e54bf8d69288fbee4904` [VERIFIED: `git hash-object -t tree /dev/null`].

### Pattern 3: Keychain secret capture via subprocess (D-09/D-10)
**What:** Store/retrieve/delete a named secret value in the OS keychain, value never on disk in the git tree.
**macOS (`security`) — [VERIFIED hands-on, this machine]:**
```bash
# STORE (value on argv — leaks to `ps` momentarily; see note):
security add-generic-password -a "$ACCOUNT" -s "$SERVICE" -w "$VALUE" -U
#   -a account (the secret key/name) · -s service (namespace, e.g. "zsh-pro:<key>") · -U update-if-exists
# RETRIEVE (value to stdout):  [VERIFIED returns exact value]
security find-generic-password -a "$ACCOUNT" -s "$SERVICE" -w
# DELETE:  [VERIFIED]
security delete-generic-password -a "$ACCOUNT" -s "$SERVICE"
```
- **Avoiding the `ps`/argv leak:** [VERIFIED] giving `-w` as the **last** option with **no value** makes `security` prompt and read from stdin — but it asks to **retype** (confirm), so you must pipe the value **twice**: `printf '%s\n%s\n' "$VALUE" "$VALUE" | security add-generic-password -a K -s S -U -w`. This keeps the value off argv entirely. **Recommendation:** prefer the doubled-stdin form for the literal-secret-capture path so the secret never appears in `ps`. Document the tradeoff; if the doubled-stdin form proves brittle across macOS versions, the `-w <value>` argv form is the documented fallback (the window is sub-second and local-only).
- **Not-found on retrieve/delete** returns a nonzero exit and `security: SecKeychainSearchCopyNext: The specified item could not be found` on stderr [VERIFIED] — detect via exit code, never surface the raw message (D-11).

**Linux (`secret-tool`, libsecret) — [CITED: man secret-tool; NOT verifiable on this macOS machine]:**
```bash
# STORE (value via stdin — no argv leak natively):
printf '%s' "$VALUE" | secret-tool store --label="zsh-pro $KEY" service zsh-pro key "$KEY"
# RETRIEVE:
secret-tool lookup service zsh-pro key "$KEY"
# DELETE:
secret-tool clear service zsh-pro key "$KEY"
```
`secret-tool` uses attribute pairs (here `service zsh-pro key <KEY>`) as the lookup schema; keep them consistent across store/lookup/clear. Mark all `secret-tool` behavior `[ASSUMED]`/`[CITED]` — it could not be exercised here.

**Backend availability detection + fallback (D-09):** probe `exec.LookPath("security")` (Darwin) / `exec.LookPath("secret-tool")` (Linux) at runtime, mirroring the `zsh`/`git` `LookPath` guard. If absent, fall back to the **git-ignored vault file** under `$ZSHPRO_HOME` (plain `kind=file`; the `.gitignore` keeps it out of every tree — verify the file path can never be added by the plumbing recipe, which only ever stages `profile.json` + `profile.zsh`). No encryption (forbidden) — protection is "not in git history."

### Pattern 4: Literal-vs-dynamic secret classification (reuse, D-08)
**What:** Decide whether a secret-named entry becomes a `SecretRef` (literal) or commits verbatim (already dynamic).
**Reuse, do not re-implement:**
- `secretRe` in `core/shell/zsh/classify.go` [VERIFIED: read] already matches `SECRET|TOKEN|PASSWD|PASSWORD|API[_-]?KEY|ACCESS[_-]?KEY|PRIVATE[_-]?KEY|CLIENT[_-]?SECRET|AUTH[_-]?TOKEN|APIKEY` against the var **name**, and `Classify` returns `CatSecrets` for such assignments. So `Entry.Category == model.CatSecrets` is the "this is a secret-named var" signal already carried on the Profile.
- The **literal vs dynamic** distinction is **already on the Entry**: `Entry.Dynamic` (Phase 2, verified) is `true` when the value contains `$(...)`/`${...}`/backticks/`$HOME`/conditionals (AST-detected, no execution). So **D-08 needs no new inspection**: `Category==CatSecrets && !Dynamic && Value != ""` ⇒ literal ⇒ convert to `SecretRef`; `Category==CatSecrets && Dynamic` ⇒ already a pointer ⇒ commit verbatim.
- **Confidence note (MEDIUM):** the `Dynamic` flag is set per-block by the parser on the assignment value; confirm during planning that `CatSecrets` entries actually carry a populated `Value` + correct `Dynamic` for the assignment forms in scope (`export API_KEY="..."` static; `export TOKEN=$(...)` dynamic). The Phase 2 `dynamic_test.go`/`parse_test.go` cover assignment values, so the signal should be present — but a `core/store`-level test should pin it explicitly rather than assume. Detection happens at classify-time in the zsh tier; the store consumes the already-tagged Entry and stays shell-agnostic.

### Anti-Patterns to Avoid
- **Importing `core/shell/zsh` from `core/store`.** Breaks the shell-agnostic seam (ARCHITECTURE.md anti-pattern). The regenerator is injected via `shell.Regenerator` at the composition root.
- **Any `git checkout` / working-tree operation in the store.** Forbidden by D-11/D-12. Reads are `git show`/`cat-file`; writes are plumbing + `update-ref`.
- **A shared "current profile" file.** Forbidden by PROF-02/D-13 (conda race). Active profile is a per-terminal env var only.
- **Surfacing raw git/keychain stderr to the user.** D-11: every error is re-phrased in zsh-pro terms; detect via exit code.
- **Resolving `$HOME`/`$(...)` anywhere in the store** (no `util.ExpandHome`). D-07/EVAL-01; dynamic values commit verbatim.
- **Re-quoting the secret value or any dynamic value.** `regen.go` already emits `Value` verbatim; the store must not `%q` it.
- **Letting the vault file be stageable.** The plumbing recipe stages exactly `profile.json` + `profile.zsh`; never glob the working tree (there isn't one in a bare repo anyway).

## Common Pitfalls

### Pitfall 1: Committing on a non-bare repo pollutes the working tree
**What goes wrong:** `update-ref refs/heads/main <commit-with-files>` on a non-bare repo where HEAD tracks `main` makes `git status` show phantom `D`eletions for files not in the working tree. [VERIFIED reproduced]
**Why it happens:** HEAD's branch now points at a tree the working tree/index doesn't match.
**How to avoid:** Use `git init --bare` (Pattern 1). No working tree ⇒ no contention ⇒ exactly the D-12 isolation guarantee, for free.
**Warning signs:** Any need to call `git status`, `git reset`, or `git checkout` in store code is a red flag — a bare-repo store never needs them.

### Pitfall 2: Non-deterministic commits break byte-stable history/tests
**What goes wrong:** Commit SHAs vary run-to-run; a round-trip test that asserts on history flakes.
**Why it happens:** `commit-tree` reads `user.name/email` from config and uses wall-clock time absent `GIT_*_DATE`.
**How to avoid:** Set `GIT_AUTHOR_*` + `GIT_COMMITTER_*` (name/email/date) in `cmd.Env` for commits, especially in tests. Assert on **content** (`git show <branch>:profile.json` → unmarshal → compare) rather than on SHAs where possible.
**Warning signs:** Flaky tests; differing `git log` between runs.

### Pitfall 3: Secret value leaks via `ps`/argv or into the git tree
**What goes wrong:** `security ... -w "$VALUE"` exposes the value to `ps` for the call's duration; or the vault file gets committed.
**How to avoid:** Prefer the doubled-stdin `security ... -w` form (value off argv) [VERIFIED]; `secret-tool store` reads stdin natively. `.gitignore` the vault file and only ever stage `profile.json`+`profile.zsh`. Never log the value.
**Warning signs:** A secret appearing in `git show <branch>` output, in `ps`, or in any error message.

### Pitfall 4: Raw git/keychain errors reach the user (D-11 violation)
**What goes wrong:** The user sees `fatal: not a git repository` or `SecKeychainSearchCopyNext: ... could not be found`.
**How to avoid:** Every subprocess call checks the exit code and maps it to a zsh-pro-phrased error type (`ErrGitAbsent`, `ErrNotInitialized`, `ErrProfileNotFound`, `ErrSecretBackendUnavailable`). Detect git absence via `exec.LookPath("git")` before the first call (mirror `introspect.go`).
**Warning signs:** Any raw stderr forwarded to the user; any test asserting on a `fatal:` substring.

### Pitfall 5: Regressing the Phase 2 round-trip oracle by changing `Entry`
**What goes wrong:** Adding a `SecretRef`/secret field to `Entry` non-additively (reordering, retyping, or making an existing field unexported) breaks `TestRegenRoundTrip` or the JSON shape.
**How to avoid:** Make the secret/ref change **additive** — a new field on `Entry` (e.g. `Secret *model.SecretRef` or a `Ref string`) with `omitempty`, leaving all Phase 2 fields untouched. Run `go test ./...` (the oracle skips cleanly if zsh absent) before and after.
**Warning signs:** `TestRegenRoundTrip`, `TestOracleProperty`, or `TestCorpusGolden` going red.

### Pitfall 6: `Read` after `Commit` doesn't byte-round-trip the IR
**What goes wrong:** `Read(Commit(p)) != p` because JSON drops or reorders a field, or a secret-converted entry can't be reconstructed.
**How to avoid:** Round-trip via `encoding/json` (deterministic) and assert `ManagedOverride`, `Dynamic`, `Category`, `Managed`, `Names`, `Value`, and verbatim `Text` survive (D-01). For secret-converted entries, the committed form intentionally differs (literal replaced by `SecretRef`) — the round-trip oracle must compare the **post-exclusion** profile, not the pre-exclusion one. Compose with the Phase 2 oracle: regenerate `profile.zsh` from the read-back profile and assert byte-identical identity tables under `zsh -f` (skip when zsh/git absent).

// Source: pattern lifted verbatim from core/shell/zsh/introspect.go (VERIFIED: read)
func (g gitRunner) run(ctx context.Context, args ...string) ([]byte, error) {
    ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()
    cmd := exec.CommandContext(ctx, "git", append([]string{"-C", g.repoDir}, args...)...)
    cmd.Env = append(os.Environ() /* + GIT_AUTHOR_*/GIT_COMMITTER_* for commits */)
    var out, errb bytes.Buffer
    cmd.Stdout, cmd.Stderr = &out, &errb
    if err := cmd.Run(); err != nil {
        return nil, mapGitError(err, errb.String()) // -> zsh-pro-phrased error (D-11), never raw
    }
    return out.Bytes(), nil
}

## Open Questions

1. **`SecretRef` placement on `Entry` and the exact JSON shape.**
   - What we know: it must be additive (Pitfall 5) and live in `core/model` (dependency-free). `kind:key` is the locked serialization (D-09).
   - What's unclear: whether to embed it as `Entry.Secret *SecretRef` vs replace the `Value` with a `kind:key` string when excluded. The latter keeps `regen.go` emitting `Value` verbatim and naturally produces `export API_KEY=keychain:API_KEY` in `profile.zsh` — but that is *not* valid runtime zsh until Ph4/5 derefs it.
   - Recommendation: planner decides; favor `Entry.Secret *SecretRef` (omitempty) + leave `Value` as a placeholder/empty so the literal never round-trips, and have the regenerator emit a clearly-non-secret placeholder. Pin the exact shape with a round-trip test.

2. **Keychain service/account naming = the dereference contract Ph4/5 reads.**
   - What we know: it must be stable and namespaced (e.g. service `zsh-pro`, account `<KEY>`; or service `zsh-pro:<KEY>`).
   - What's unclear: whether the key should be scoped per-profile (so two profiles can hold different values for the same var name) or global-by-name (D-07's "value store keyed by name in one place"). The CONTEXT specific-idea says "keyed by name in one place, referenced per-profile" ⇒ **global-by-name**.
   - Recommendation: global-by-name keychain entries (one value per secret name), referenced per-profile via `SecretRef`. Lock this now; Ph4/5 derefs by name.

3. **Does `Commit` ingest a `model.Profile` only, or also handle the not-yet-built ingest path?**
   - Resolved by scope: Phase 3 proves `Read(Commit(p)) == p` against an **in-memory `model.Profile`**; the real `~/.zshrc` on-ramp is Ph6. No open work here — just don't pull Ph6 forward.

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
