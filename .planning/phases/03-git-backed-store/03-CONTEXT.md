# Phase 3: Git-Backed Store - Context

**Gathered:** 2026-06-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Build `core/store` — a **git-backed persistence layer** for the Phase 2 `model.Profile` IR, where **each git branch is an environment profile**. The store initializes a git repo via the `git` binary (no new Go dependency; mirrors the `zsh -f` subprocess + timeout + graceful-degrade pattern), exposes `Init` / `Branches` (list) / `Current` / `Checkout` / `Read` / `Commit` typed in terms of `model.Profile`, tracks the active profile **per-terminal** via an env var (never a global file), and excludes detected secrets from the committed tree by default via a reference/deref model.

**In scope:**
- `core/store` package: repo init, list/create/select-profile, `Read`/`Commit` round-trip of a `model.Profile`.
- On-disk layout: `profile.json` (authoritative IR serialization) + a single source-ordered `profile.zsh` (regenerated via Phase 2's `regen.go`) per branch.
- Per-terminal active-profile tracking (env-var-carried; profile name only).
- Secret handling: detect literal secrets, convert to a `SecretRef` pointer, capture the value into a resolver backend, exclude the literal from the committed tree, and report what was withheld. (The **deref-on-switch** that reads the value back and sets the env var is Phase 4/5.)
- git absent / errors degrade with a clear, zsh-pro-phrased message.

**Not in scope (later phases):**
- The runtime `Manifest` build + per-category emit + activate/deactivate (Ph4, SW-01/SW-02).
- The sourced loader/CLI verbs + `.zshrc` bootstrap block + the env-var *export* on switch (Ph5, BOOT-01/02).
- **Dereferencing** secret pointers at activation (reading the value from keychain/file and setting/unsetting the env var) — Ph4/5.
- End-to-end ingest of a **real** `~/.zshrc` into the `main` baseline (parse → classify → partial-eval → commit, master-block routing, idempotent install) — Ph6, PROF-03 end-to-end. Phase 3 proves the Read/Commit round-trip against a `model.Profile`; it does not own the real-file on-ramp.
- Per-category `.zsh` emit (Ph4); PATH add/delete segmentation (Ph4).
- No filesystem / `$HOME` / `$(...)` resolution, ever (no `util.ExpandHome` in the store path).

</domain>

<decisions>
## Implementation Decisions

### Store layout & serialization format
- **D-01: `profile.json` is the authoritative, lossless serialization of `model.Profile`.** Every derived field — `ManagedOverride`, static/dynamic tag, category, declarative/imperative verdict, verbatim `Block.Text` — must survive serialization (Phase 2 stated these "must survive into Ph3/Ph4"). JSON is the only candidate that preserves them without re-running the parser/classifier, so the store stays shell-agnostic (no re-parse on `Read`). Structured git diffs are a bonus. (Rejected: per-category `.zsh`-only and single source-ordered `.zsh`-only — both lose the derived fields unless the store re-parses, which couples it to a parser and breaks the shell-agnostic seam.)
- **D-02: Commit a single source-ordered `profile.zsh` alongside the JSON, for human browsing and meaningful diffs.** It is a **derived view** (JSON is authoritative); generated by **reusing Phase 2's existing `core/shell/zsh/regen.go`** in source order. No new emit code, no Phase 4 pull-forward, honors Phase 2 D-09 (per-category emit is Phase 4). (Rejected: per-category `.zsh` now — reopens the cross-category load-order hazard D-02/D-09 guarded against and pulls Phase 4 forward.)
- **D-03: `.zsh` emission goes through an injected regenerator seam, not a direct import.** `core/store` stays shell-agnostic and must not import `core/shell/zsh`; the regenerator is injected at the composition root (mirroring the `shell.Provider` pattern). Exact seam shape is Claude's discretion (see below).

### Repo location & baseline
- **D-04: Store repo lives at `$XDG_DATA_HOME/zsh-pro` (default `~/.local/share/zsh-pro`), overridable via `$ZSHPRO_HOME`.** XDG_DATA_HOME is the correct spec location for tool-managed app state (a git store is data, not user-edited config).
- **D-05: The git default/baseline branch is `main`; it holds the (eventually) ingested `~/.zshrc`.** `create <name>` forks `main` (every profile shares a clean common ancestor). (Rejected: forking the *current* profile — profiles could diverge from baseline confusingly.)
- **D-06: `Init` is idempotent and never clobbers an existing repo.** Re-running `Init` on an existing store is a safe no-op. An absent `git` binary degrades with a clear, zsh-pro-phrased error (criterion #1) — never a crash, never a raw git error.

### Secrets — reference/deref model (elevates PROF-03)
- **D-07: Secrets become late-bound *pointers*, not dropped values — consistent with EVAL-01.** A secret is treated as one more late-bound value (the same philosophy that keeps `$HOME`/`$(...)` unresolved). The committed profile stores a **reference**; the literal value never enters the git tree.
- **D-08: Distinguish literal vs already-dynamic secrets.** A secret-named var whose value is **already dynamic** (e.g. `export TOKEN=$(op read ...)`) has no literal value and is **committed verbatim** (it is already a pointer / late-bound). Only **literal** secrets (`export API_KEY="sk-abc123"`) are converted to a `SecretRef`.
- **D-09: `SecretRef` is a resolver-agnostic pointer that serializes into the Profile now.** Shape: `kind:key` (e.g. `keychain:API_KEY`, `file:API_KEY`, `cmd:'op read ...'`). Default backend = **OS keychain via subprocess** (`security` on macOS / `secret-tool` on Linux — mirrors the `zsh -f` / `git` binary pattern; no plaintext on disk; no new dependency), with a **git-ignored vault file** as the portable fallback. Future managers slot in as new `kind`s.
- **D-10: Phase 3 builds full exclusion (not just a hook).** On `Commit`, literal secrets are detected (reusing the shipped secret detector), captured into the resolver backend, replaced by a `SecretRef` in the committed Profile, and a **withheld-report** (name + source line) is returned for the CLI to surface. The **deref side** (reading the value back, setting/unsetting the env var at activation) is Phase 4/5. *Traceability note for the planner:* update REQUIREMENTS.md so PROF-03 is marked as *starting* in Phase 3 (store-side exclusion + reference), with the runtime deref completing in Ph4/5 and the real-`~/.zshrc` end-to-end path in Ph6.

### Per-terminal isolation & checkout safety
- **D-11: Git is fully abstracted behind zsh-pro verbs — the user never touches raw git.** All operations are wrapped by `zsh-pro` commands (`checkout` / `create` / `list` / `status`); there is no user-facing working tree to `cd` into and edit; all errors are phrased in zsh-pro terms, never as raw git output. This is a hard UX principle for the whole store surface.
- **D-12: Read profiles via `git show <branch>:<path>` from the object DB — never a user-facing checkout.** The working-tree HEAD is an internal implementation detail (it can stay on `main`). This gives true per-terminal isolation with zero shared-HEAD contention (the conda concurrent-activation race PROF-02 forbids), and keeps git fully hidden per D-11. `Commit` writes to a target branch via plumbing (temp index / `commit-tree` + `update-ref`) so one terminal's commit never disturbs another's. (Rejected: a git worktree per terminal — heavier, lifecycle/cleanup cost; plain `git checkout` of a shared HEAD — reintroduces the forbidden race.)
- **D-13: The active profile is tracked per-terminal in an env var carrying the profile name only** (e.g. `ZSHPRO_PROFILE=work`). The repo path derives from `$ZSHPRO_HOME` / XDG (single store in v2.0). `Current()` reads the env var; **unset ⇒ `main` (baseline)** implicitly. (The env var is *exported* by the sourced loader in Ph5; Phase 3 defines the contract — the var name and that it carries the name only — and `Current()`/`Checkout` read/honor it.)

### Claude's Discretion
- Exact `core/store` API signatures (`Init`/`Branches`/`Current`/`Checkout`/`Read`/`Commit`), package placement, and the regenerator-seam interface shape (D-03) — provided the shell-agnostic constraint and the per-terminal/`git show` model hold.
- The git plumbing approach for committing to a non-checked-out branch (temp index via `GIT_INDEX_FILE` + `write-tree`/`commit-tree`/`update-ref`, vs an alternative) — provided no working-tree HEAD is disturbed (D-12) and no new dependency is added.
- Commit granularity (full snapshot per commit vs diff), commit-message conventions, and `list`/`status` output shape.
- The resolver backend implementation details (keychain subprocess invocation, vault-file format/location under `$ZSHPRO_HOME`) — provided no new dependency and no encryption dependency, and the `SecretRef` `kind:key` serialization (D-09) is stable.
- The exact env var name (D-13).

</decisions>

## Existing Code Insights

### Reusable Assets
- `core/shell/zsh/regen.go` (Phase 2): regenerates a behavior-equivalent source-ordered `.zsh` from a `model.Profile` — directly produces `profile.zsh` (D-02), invoked via an injected seam (D-03).
- `core/shell/zsh/introspect.go`: the canonical sandboxed-subprocess shape (`exec.CommandContext` + 5s timeout + degrade-when-absent). The `git`-binary store ops (PROF-01) and the keychain resolver (D-09) follow this exact shape.
- The shipped secret detector (`secretRe` in `core/shell/zsh/classify.go`, surfacing `has_secrets`): reused to flag literal secrets for D-08/D-10.
- The Phase 2 round-trip oracle (`02-VERIFICATION.md`): the store's `Read(Commit(p)) == p` round-trip composes alongside it.

### Established Patterns
- `core/model` stays dependency-free; the store types/serialization belong with `core/model` (Profile) + a new `core/store` package. `core/store` must **not** import `core/shell/zsh`; shell-specific regeneration is injected at the composition root (`core/cmd/zsh-pro/main.go`) — the only place concrete shell impls are wired.
- Sandboxed subprocess with timeout + graceful degradation (mirror `zsh -f`) for **every** external binary: `git` and the keychain CLI. An absent binary degrades with a clear zsh-pro-phrased error (D-06, D-11), never a crash.
- TDD: a `Read(Commit(profile))` round-trip test is the Phase 3 correctness pin; it should assert `ManagedOverride` + static/dynamic tags + verbatim text survive (D-01).

### Integration Points
- Input: a `model.Profile` (from Phase 2's IR build) handed to `Commit`.
- Output consumed downstream: Ph4 (manifest builder reads the persisted Profile via `Read` to produce the `Manifest`), Ph5 (loader exports the `ZSHPRO_PROFILE` env var on switch and dereferences `SecretRef`s at activation), Ph6 (the real-`~/.zshrc` ingest path commits the baseline into `main`).
- The `SecretRef` (D-09) and per-terminal env-var contract (D-13) are contracts Ph4/5 depend on — they must be defined here even though their *runtime* use is later.

<specifics>
## Specific Ideas

- **User idea (2026-06-27) — secrets as pointers, dereferenced on switch:** rather than dropping secrets, store a reference and resolve it at activation time. Recognized as the EVAL-01 late-binding philosophy applied to secrets; drove D-07–D-10 (the whole reference/deref model) and dissolved the "git-ignored sidecar bleeds across branches" problem (the value store is keyed by name in one place, referenced per-profile).
- **User principle (2026-06-27) — git fully abstracted:** "the user should not have to tinker with git at all… the git part is completely abstracted." Drove D-11 (zsh-pro verbs only, errors in zsh-pro terms) and reinforced D-12 (read via `git show`, no user-facing checkout / working tree).

</specifics>
